# QuickCart release regression — local exercise runbook

**Owner:** application-oncall (learner role); **backup/release operator:** release-engineer; **recovery reviewer:** independent-reviewer. These are fictional duties, not an actual staffing commitment. Status: Draft; exercised locally 2026-10-15. No external notifications are sent.

1. **Detect:** Inspect the versioned report and sample/review counts. Unsafe ready output or insufficient evidence blocks release. Coverage below .75, failures above .10, quality below .95/drop above .05, p95 above 1000 ms or cost/request above hypothetical $.01 halts this exercise. Gates are fixed in `watch.py`, minimum window eight, complete review required. Production thresholds require discovery and representative evidence.
2. **Contain:** Application-oncall halts rollout and records candidate artifact, symptom, scope, owner and next update. Keep support in the established review route; count review backlog rather than claiming fallback success. Do not retry side effects speculatively. This CLI writes a local halt file only; real traffic routing must enforce the halt.
3. **Diagnose:** Preserve baseline/canary reports, gate and artifact hashes. Compare config/data/model/prompt/schema. Inspect routine versus slow counts and missing review. Test competing hypotheses: reduced timeout, provider outage, changed traffic mix, data freshness. Correlation alone is not a diagnosis. Synthetic manifests differ only by timeout.
4. **Restore:** Release operator verifies registry identity and schema compatibility, then restores the whole known-good manifest. Never restore revoked access or deleted data. If provider failure affects both versions, keep capability disabled and use bounded manual review; do not mark old-code deployment as recovery.
5. **Verify:** Read actual active manifest back, replay probes and compare all gates and slices. Preserve fresh recovery report. In a service also check queues, current permissions, duplicate effects, saturation and reviewed semantic output; a health endpoint alone cannot certify recovery.
6. **Review/resume:** Keep rollout halted until a separate reviewer accepts the evidence and a bounded new rollout is authorized. The reference never resumes automatically. If probes fail, retain the halt and investigate; do not edit gates to pass.
7. **Learn/dispose:** Record factual timeline and write a concrete runbook amendment with owner/test. Expire event rows at seven days and inspect deletion count; separately manage backups/exports in a real system. Retain only sanitized local evidence for the exercise, then use workbook cleanup.

**Communication exercise:** Write (do not send) a support update with impact, current containment, uncertainty, named owner and next update time. Example wording for this synthetic incident: “Four of ten probes failed after the timeout change, including two answerable cases. Rollout is halted; the prior configuration passes recovery probes. Review is pending before resuming. Application-oncall will update the exercise record at the next review checkpoint.” Do not use logical minutes as real response-time evidence.

**Exercise amendment:** The generated `runbook-update.md` records the observed 500 ms regression. Before proposing timeout changes, replay slow answerable and abstaining cases, verify coverage/failure denominators and review queue capacity. Application-oncall owns the regression check; reviewer owns resume. This amendment is supported by the synthetic recovery replay, not an actual customer incident.
