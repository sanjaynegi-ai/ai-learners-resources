W-LLM-API-02 compared two prompts on ten replayed cases. Real release decisions need more:
- **a fixed dataset**, versioned, with a **development split** you iterate on and a **held-out split** you only use for decisions;
- **per-case scoring** against an answer key decided beforehand;
- **slices** and **denominators** with confidence intervals;
- **latency and cost**, not just quality;
- **release gates** written down before you look, including **critical gates** that nothing can outweigh;
- **run records** that let anyone reproduce or question a decision.

This harness does all of that for the refund-draft pipeline, using the real pipeline code (`draft_reply`, the schema, the business checks), and a **simulated model**.

**Intuition:** this is the CI pipeline for behavior that unit tests cannot pin down. Like CI, it only protects you if the checks were written before the change and nobody quietly edits them to get a green build. The analogy's limit: CI tests are deterministic and exhaustive for what they cover, while evaluation scores are samples with uncertainty, and a test set can be used up by looking at it too often.

| Component | Real or simulated |

| Model behavior, latency, token counts | **Simulated** (`simulated_model.py`), per-prompt-version profiles, seeded and reproducible |
| Prices | **Hypothetical** ($0.50 per million input tokens, $2.00 per million output tokens) |

## The dataset and the gates

`data/cases.json` (generated by `src/eval_harness/dataset.py`; `--check` verifies it) holds **75 synthetic cases**: development 30, held-out 45. They cover three languages (en, de, hi) and five categories:
- `issued`: should answer;
- `pending`: should escalate;
- `not_requested`: should escalate;
- `out_of_scope`: should escalate;
- `injection`: should answer, ignoring the injected instruction.

Development and held-out **share no ticket text**. Each case's expected outcome comes from its order facts and category, not from any model.

**Scoring per case:**
- **correct:** an expected escalation came back `needs_agent`; or an expected answer came back `ready` with the right date, in the right language, and with no unsupported amount or claim.
- **harmful:** a `ready` draft that should not be sent: the case should have escalated, the date is wrong, it contains an unsupported amount, or it claims an unissued refund was issued.

`data/gates.json` (`release-gates-2026.10-a`) was fixed before any comparison:
- **Critical:** 0 harmful ready drafts on held-out.
- **Non-regression:** correct and coverage may not fall more than 5 points against the baseline, and no slice with 9 or more cases may fall more than 15 points.
- **Quality:** at most 15% of ready drafts in the wrong language.
- **Operations:** latency p95 of 8 s or less; cost of $1.00 or less per 1,000 requests.

Every decision prints the gates' **fingerprint** (`23f68d8a90657598` for the reviewed version), a hash of the thresholds themselves.

## Guided decision 1: v2 against production v1

**Read the denominators before comparing:** this harness calls correct answers on **answerable cases** divided by all answerable cases `coverage` (6/18 or 13/18 below). That differs from ready/all-request coverage used in other course labs. Correct outcomes use all 45 cases; harmful and wrong-language rates use returned ready drafts. Keep the local metric definition beside each figure rather than comparing unlike percentages.

> [!IMPORTANT]
> Held-out data becomes development evidence when its results guide a change. Version names and reuse warnings help identify that drift; they do not restore independence or certify the release process.

Production runs `refund_reply_v1`. The team proposes `refund_reply_v2`. **Predict** the decision, then run:

```powershell
uv run eval-harness decide --baseline refund_reply_v1 --candidate refund_reply_v2
```

**Observed (held-out, simulated):**

| | Correct | Coverage | Harmful ready | Wrong language (ready) | Latency p95 | Cost per 1,000 |
|---|---|---|---|---|---|---|
| v1 | 20/45 | 6/18 | **18/29** | 16/29 | 3.39 s | $0.3564 |
| v2 | 35/45 | 13/18 | **6/21** | 7/21 | 6.26 s | $0.4975 |

**Decision: NO-RELEASE.** Failed gates: harmful ready drafts (critical), `slice category=pending` (6/9 against v1's 8/9), and wrong language on ready drafts.

<details><summary>Reading it</summary>

v2 is far better *on average* (correct 20 → 35), and still not releasable. Six ready drafts would mislead customers, and nothing in the averages can buy that back. The slice gate catches what the averages hide: on pending refunds, v2 is *worse* than v1, because it more often says "your refund has been issued". Latency p95 doubled because v2's malformed outputs trigger retries, which only shows up because latency is part of the gates. Note the intervals: 35/45 is a 95% interval of about 64%–88%, not "78%, full stop".

</details>

## Fault drill: moving the goalposts

After the NO-RELEASE, someone edits `data/gates.json`: harmful maximum 6, slice drop 25, wrong-language rate 0.35. They leave `gates_version` unchanged. Make that edit yourself and rerun the decision.

**Observed:** `Decision: RELEASE`, with `harmful ready drafts: 6/21 (max 6)`, under the same version name `release-gates-2026.10-a`. Only the fingerprint changed, to `f51038fecdd646eb`.

**Diagnosis:** gates edited after seeing results no longer represent the original release criteria. Review thresholds like code, retain the reviewed fingerprint and reject decisions evaluated under unapproved changes. The fingerprint test detects threshold changes, not mere line endings. **Repair:** reverse only this drill's threshold edits, preserving any unrelated work; rerun and confirm the reviewed fingerprint `23f68d8a90657598` and NO-RELEASE.

## Unfamiliar failure: the release that should not happen

The team comes back with `refund_reply_v3`: "v2 plus a few worked examples of difficult tickets". They run the decision:

```powershell
uv run eval-harness decide --baseline refund_reply_v1 --candidate refund_reply_v3
```

**Observed:** every gate passes, with 41/45 correct, **0/16 harmful**, cost $0.7317 per 1,000, under the reviewed gate fingerprint. **Decision: RELEASE.**

Your manager asks you to sign off. **Before you do, investigate.** You have not been told what is wrong, or whether anything is. Use the tools you have: `run --split dev --cases` for v2 and v3, the registry, and the prompt files in `../refund-drafts/src/refund_drafts/prompts/`. Write a short investigation note: what you checked, what you found, what you recommend, and what process change prevents it next time.

<details><summary>Hint 1</summary>

Compare v3 with v2 on **development** and on **held-out**. Which one improved?

</details>

<details><summary>Hint 2</summary>

Read v3's examples. Then search `data/cases.json` for their ticket texts.

</details>

<details><summary>Worked reasoning</summary>

- **Dev did not improve; held-out did.** v3 on development is identical to v2 (24/30 correct, **4/14 harmful**, the same cases D-005, D-013, D-014 and D-020). On held-out it jumps from 6 harmful to 0. This pattern motivates investigation; it is not proof of contamination by itself. The matching examples below supply the direct evidence.
- **The examples are held-out cases.** All six example tickets in `refund_reply_v3.txt` are copied verbatim from held-out cases v2 got wrong (H-035, H-049, H-050, H-054, H-056, H-058). One text also matches a seventh held-out case. The simulated model, like a real one, reproduces answers it was shown. The held-out score now measures memory of those cases, not behavior on new tickets: **evaluation contamination** (SG-ML-01's L6).
- **Recommendation:** do not release. v3's general quality is unknown; its development results remain useful diagnostics and still expose harmful drafts, but are not an unbiased unseen-performance estimate. Rebuild examples from a separate example pool and obtain fresh held-out cases before a new release claim.
- **Process:** add a contamination gate (next section), keep example pools separate from evaluation data, and watch the registry's held-out reuse warning.

</details>

## Independent exercise: a contamination gate

Implement `find_contaminated` and `contamination_gate` in `exercises/contamination.py`, following the docstring: verbatim matches after normalizing case and whitespace, or shared runs of six or more words. Then:

```powershell
uv run python exercises/check_contamination.py
```

**Expected:** `contamination: contamination checks passed (7 contaminated held-out cases block v3)...`. The check verifies:
- toy cases, including the six-word boundary;
- that v1 and v2 are clean;
- that v3's contaminated cases are exactly those whose text appears in its prompt;
- that `decide(..., extra_gates=(contamination_gate,))` turns v3 into **NO-RELEASE** while v2 passes this gate.

The untouched starter raises `NotImplementedError`; `--reference` runs `contamination_reference.py`.

<details><summary>Progressive hints</summary>

1. Normalize both texts the same way before comparing.
2. Short tickets (four words, such as "Ist meine Rückerstattung unterwegs?") need the verbatim rule; longer edited copies need the n-gram rule.
3. The gate only needs held-out cases. Development cases in examples are a smaller problem; explain why in your note.

</details>

<details><summary>Worked reasoning</summary>

Contamination detection is cheap insurance: text overlap is checkable before any model call. It is not complete. A paraphrased example ("I posted the item back, when is my money coming?") shares meaning, not six consecutive words. That is why the *process* control (separate example pools, fresh held-out sets, a reuse counter) matters as much as the check. Development cases appearing in examples is normal practice: that is what development data is for.

</details>

## Troubleshooting

| Symptom | Likely cause | Diagnostic and repair |
|---|---|---|
| `ModuleNotFoundError: refund_drafts` | The editable path dependency is not installed | Run `uv sync` in this directory; `pyproject.toml` points to `../refund-drafts`. |
| `UnicodeEncodeError` in reports | Windows console code page | `$env:PYTHONIOENCODING = "utf-8"`. |
| `cases.json differs from the generator` | Data edited by hand, or line endings changed | Regenerate with `python -m eval_harness.dataset`; `.gitattributes` pins LF. |
| `Release decisions use the held-out split` | `decide` was given development runs | Iterate on dev; decide on held-out. |
| A reuse WARNING appears | Many prompt versions were scored on held-out | Refresh held-out cases before trusting small differences; that is the warning's purpose. |
